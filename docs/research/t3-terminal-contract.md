# Map supported T3 Code interfaces to the Core terminal contract

Neither route satisfies Core terminal v2 on T3 Code 0.1.11. T3 lets a person open, use, and close integrated terminal tabs. The host CLI and external Model Context Protocol (MCP) expose native chats, but neither exposes the owned terminal tab operations Runner needs after its launcher turn ends. [Research issue][issue] · [Core contract][core] · [T3 host and external interfaces][outside] · [Terminal controls][drawer]

## Versions and evidence

On 2026-11-23, the running Linux x86-64 desktop executable belonged to Debian package `t3code 0.1.11 amd64`. The host reported `t3 v0.1.11` and `codex-cli 0.171.0`. `t3 thread list --project . --json` succeeded against the running host. The analysis uses the installed CLI’s help, this research thread’s advertised MCP catalog, and upstream sources pinned to the desktop release. External MCP authorization and desktop interactions remain untested. [T3 release][release] · [Host CLI source][cli] · [MCP registration][mcp]

The Core reference is `issue-runner-core` 1.0.3 at `ac3fcc409da0596823fc5545d3d584e5906c0dfc`, with terminal contract 2 and independent enhancement contract 3. The comparison adapter is `issue-runner-herdr` 1.0.2 at `f715b94e1864fa19a1c3766dbe2c7811a022f2f8`, which targets Herdr 0.9.5. Its documented tab and pane protocol shows the capabilities a terminal backend supplies. [Core exports][types] · [Core contract][core] · [Herdr protocol][herdr]

## Launcher handoff

- **Desktop.** A person can toggle the launcher thread’s terminal drawer, open a new terminal, and start Runner in that shell, either directly or via a saved project action. T3’s environment server owns the integrated terminal and its process lifetime. The docs describe running terminal commands surviving thread settlement by default. This supports the proposed lifetime but leaves the exact launcher-turn transition for a desktop test. [Keybindings][keys] · [Terminal controls][drawer] · [Terminal runtime][runtime] · [Settlement behavior][settle]
- **Launcher AI.** The advertised MCP catalog and the release’s MCP registration have no tool to open an integrated terminal or start a saved action in it. A provider shell tool launches provider-managed work. `t3 app <path>` opens a native thread for a project in a running local desktop app. Neither supplies an integrated terminal handle. The launcher AI opening and starting Runner in the integrated terminal is therefore already blocked on the checked public interfaces. [MCP registration][mcp] · [Provider shell ownership][settle] · [`t3 app` docs][app]
- **Runner process.** Host scripts can use `t3 thread` without separate sign-in. External clients can separately authorize `/mcp` over loopback HTTP or a supported HTTPS connection. Read-only approval allows inspection. A write-capable approval permits native thread launch, messaging, and interruption within its permission ceiling. Some tools appear in discovery but require an in-T3 agent. The v0.1.11 terminal environment adds `T3CODE_THREAD_ID` for the containing thread. That ID identifies a chat and grants no terminal operations. [Outside agents and host scripts][outside] · [v0.1.11 release notes][release]

## Contract mapping

Core’s public `runCli` drives the plugin. Each Runner Tab gets an opaque handle and bound `TerminalIO`. The adapter checks revocation before queued input starts, bounds backend operations, and rejects errors without guessing a replacement target. Herdr exposes explicit native IDs and separate calls for tab creation, visible screen, literal input, and closure. [Core contract][core] · [Herdr protocol][herdr]

| Core requirement | Agent CLI in a T3 integrated terminal | Native T3 AI chat |
| --- | --- | --- |
| `createTab({ cwd, env, label, submitKey, signal })` creates an owned shell tab with an absolute working directory and inherited environment plus overlay. Agent startup happens later. | Desktop **New Terminal** creates a visible shell within the thread’s terminal UI. No exposed command or tool gives Runner a distinct terminal ID, applies the requested context, or binds I/O to that tab. [Terminal controls][drawer] · [MCP registration][mcp] | `t3 thread start` creates a native chat with a first message. MCP `t3_thread_launch` can also create an idle native thread by omitting the prompt and attachments. The title names a conversation. Its ID carries no terminal control or per-tab environment overlay. [Host CLI source][cli] · [MCP launch schema][launch] |
| `execute(handle, command)` submits Core’s opaque shell start or exact-session resume command, then `Right` and `Enter`. It resolves on input delivery. | A person can run the command in the chosen shell. Project actions can run saved shell commands, and may reuse an idle drawer terminal. No exposed operation accepts an arbitrary command for the exact owned terminal. [Terminal controls][drawer] · [Project action terminal selection][reuse] | CLI and MCP launch a configured provider in a project, and `send` submits a prompt. CLI `--worktree <base>` creates a new checkout. A CLI path inside an existing worktree selects its project and does not bind the thread to that path. The release’s MCP schema supports `workspaceStrategy.type = "existing_worktree"` for a project worktree. This can address worktree selection, but the launch schema offers no arbitrary `cwd` or environment overlay, nor Core’s shell start/resume semantics. [Host CLI docs][outside] · [Host CLI path resolution][cli-path] · [MCP launch schema][launch] |
| `TerminalIO.read()` returns the current visible plain-text screen. | A person can read the viewport or copy terminal output. The server saves bounded scrollback for reconnection. Runner has no supported viewport read, and retained output can differ from the rendered screen. [Terminal history][terminal] · [Terminal runtime][runtime] | `t3 thread show` and MCP `t3_thread_read` expose messages or activity. A chat timeline does not contain the current rendered terminal screen. [Host CLI docs][outside] · [MCP thread tools][orch] |
| `TerminalIO.submitText(text)` submits the complete LF-normalized literal body, then `Right` and the tab’s configured submit chord. | A person can paste and submit through the focused terminal. No exposed tool performs that sequence as one bound operation. [Terminal history][terminal] · [Keybindings][keys] · [MCP registration][mcp] | CLI `t3 thread send` accepts a message or reads it from stdin. MCP `t3_thread_send` submits or steers a native chat message. A busy thread queues the CLI message for a later turn. These are prompt operations, with no terminal paste or submit chord. [Host CLI docs][outside] · [MCP thread tools][orch] |
| `TerminalIO.sendKeys(keys)` sends supported logical chords in order and rejects unsupported keys. | The desktop accepts keyboard input in the focused terminal. No exposed process API sends ordered keys to a tab by identity. [Keybindings][keys] · [MCP registration][mcp] | Native chat has composer controls and an interrupt operation for an active run. Neither gives Runner a terminal key channel for interactive Agent controls. [Composer and terminal shortcuts][keys] · [MCP thread tools][orch] |
| Core verifies the handoff before closure. | Core reads the assigned file, validates it through the stage’s acceptance function, and persists acceptance before requesting closure. A task writing to the same filesystem can fulfill this independently of T3 status, provided Runner can start the task and deliver its Assignment. [Core stage flow][stage] | A native chat can also write the assigned file if its workspace and permissions allow it. `--wait`, `t3_thread_wait`, assistant text and a Settled thread report T3 state. Core still requires the validated file. [Core stage flow][stage] · [Host CLI docs][outside] |
| `closeTab(handle)` removes only the actual owned tab, even after input revocation. | The desktop has a close control per terminal row plus a focused-terminal shortcut. Runner has no supported close-by-terminal-ID operation. [Terminal close control][close] · [Keybindings][keys] · [MCP registration][mcp] | `t3_thread_interrupt` targets a run. `t3_thread_organize` changes thread state, including settle, archive and their reversals. These operations accept a thread ID. Neither surface exposes a command to close the actual desktop task tab by an owned handle. [MCP thread tools][orch] · [Thread organization schema][organize] · [Acceptance criteria][epic] |
| Recover the task conversation after closure or interruption. | The Agent CLI owns the conversation. With Codex, `codex resume <session-id>` can reopen the exact saved session from a new shell if its storage and required workspace context remain available. Core records the native reference via a Session Probe or enhancement and substitutes it into the configured resume command. T3 terminal scrollback is a separate record. Exact recovery after a real tab close remains unverified. [Codex resume][codex] · [Core lifecycle][core] · [Terminal history][terminal] | T3 saves the thread timeline. Reopen the thread from the sidebar or its link, read it with `t3 thread show` or MCP `t3_thread_read`, and continue the same T3 thread through the composer or a send command. Provider-native continuation depends on provider support. A T3 thread ID identifies the timeline and does not establish Core’s native session reference or exact shell resume. [Thread history and continuation][sidebar] · [Host CLI docs][outside] · [Portable handoffs][portable] · [Core lifecycle][core] |

## Limits of project actions and other routes

- **Settlement and project actions.** Settling can close idle terminal prompts and keep their output. An active command can remain open. An action marked `stopOnSettle` can stop a terminal running that action. A `runOnSettle` action can run worktree cleanup in its own terminal. These rules apply at thread scope and select terminals by state or action. Core needs explicit closure of the exact tab it owns after accepting the handoff. An action that starts Runner could keep it running, but would still leave Runner without the tab API. [Settlement behavior][settle] · [Project action terminal selection][reuse] · [Acceptance criteria][epic]
- **Shell and project configuration.** `T3CODE_TERMINAL_SHELL` selects an executable for new interactive terminals on the host. It has no command arguments or per-tab overlay. `t3 project add <path>` can register a project root for a native chat. That creates project state and still supplies no terminal I/O. [Shell selection][shell] · [Host project toolkit][launch]
- **Other control paths.** A nested multiplexer or Runner-owned pseudoterminal can own subprocesses, but its panes are outside T3’s native tab lifecycle. Provider shell tools and a process stop control target jobs, and a prompt link opens a draft. Internal app transport, GUI automation, and application changes are outside acceptance. [T3 terminal runtime][runtime] · [Thread process stop behavior][process] · [Prompt links][prompt] · [Acceptance criteria][epic]

## Desktop evidence for issue 3

Record the versions again if any components change. Test the supported steps independently on the pinned build and record the first unavailable operation for each route. [Desktop experiment][experiment] · [Acceptance criteria][epic]

1. Open a launcher terminal manually, start a harmless long-running command there while a launcher turn runs, and observe that it still runs after the turn ends. Record who opened the terminal and who started the command. This establishes process lifetime only if a person performs the launch.
2. Check the terminal UI with two distinct tabs. Record their working directory and environment, paste multiline text, try the configured submit chord, and close only the task tab with its own control. Resume the Agent CLI’s exact saved session in a fresh terminal. Record what survives in the Agent’s history and in T3.
3. Independently check native thread launch, worktree binding through authorized MCP, and history reopening by thread ID. Record what the desktop shows after a run ends, after settlement, and after reopening. Count Core-verified handoff and Runner-owned tab closure as separate acceptance evidence only when the public Core workflow actually performs them.
