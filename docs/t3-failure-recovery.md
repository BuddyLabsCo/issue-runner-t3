# T3 failure and native recovery signals

Research for [issue #52](https://github.com/BuddyLabsCo/issue-runner-t3/issues/52). Source baseline: [T3 Code v0.1.12](https://github.com/pingdotgg/t3code/releases/tag/v0.1.12), commit [ca81b7b](https://github.com/pingdotgg/t3code/tree/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd), and the [Codex enhancement at 7bffcb3](https://github.com/BuddyLabsCo/issue-runner-agent-codex/tree/7bffcb348c1fd7b6c0f75505f72ac2cabbf1040d). The findings come from the pinned source, not live failure injection or provider acceptance testing.

## What the public interface can establish

| Signal | What it establishes | What it does not establish |
| --- | --- | --- |
| `t3_thread_read.recentRuns[].status` | Terminal outcome of an identified run, including `failed`, `interrupted`, `cancelled`, `rolled_back`, and `completed`. | Cause, retryability, whether a native continuation is scheduled or which later run continues it. |
| `thread.status`, `activeRunId`, `latestRunId`, requests and background-work metadata | Current activity and latest result. Active status takes precedence; a failed result takes precedence over background-work waiting. | Whether a terminal run's recovery is pending; thread status alone is insufficient to establish quiescence. |
| Activity timeline `type: "error"`, `status`, `title`, `text`, `runId`, `sourceThreadId` | A diagnostic belongs to that run; a running error item can indicate a provider retry. | A generic error item is not a failed run; text and title are presentation fields, not a typed classification or retry contract. |
| `t3_thread_wait` with explicit run ID | Waits for settlement; follows existing restart continuation lineage and suppresses settlement while a restart continuation effect is pending. Returned run ID may differ from input. | Timeout does not establish a failure or explain why the run is unsettled; it does not follow usage-limit continuation lineage in the same way. |
| `snoozed`, `snoozedUntil` | Thread visibility/snooze state. | Whether a usage-limit recovery is armed: auto-resume and snooze are independent. |
| MCP Events `thread.run_settled` | Run ID and terminal outcome after a started run ends. | Error class, retry schedule, or failures before the run started. |
| MCP call error `code`, e.g. `provider_unavailable`, `model_unavailable`, `orchestration_error` | A tool request failed. | The outcome of a previously acknowledged provider run. |

## Internal failure and retry semantics

T3 already normalizes failures to `class` (usage limit, provider, transport, permission, validation, unknown), `code`, nullable `retryable`, optional `resetAt`, and safe human-readable message. An optional retry record includes attempt, nullable maximum attempts, and nullable delay. These fields live on error items. The thread shell also has `lastErrorClass`, `lastErrorCode`, `usageLimitResetAt` and `limitRecovery`; none is included in the external read result. [Failure/retry schema](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/orchestrationV2.ts#L1718-L1756), [error item](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/orchestrationV2.ts#L2049-L2054), [shell schema](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/orchestrationV2.ts#L2436-L2476).

The shared builder defaults to class `unknown` and `retryable: null`; it marks request-too-large failures as non-retryable. A retry record on a failed item can be historical: ongoing retries use status `running`, successful ones `completed`, and failed or stopped ones terminal status. The builder emits titles such as “Provider retry”, “Provider recovered”, and “Usage limit reached”. These titles provide useful diagnostic clues for this pinned version but the public interface does not define them as an exhaustive classification. Even internally, `retryable: true` does not mean a retry has been scheduled, and a nullable value is uncertainty, not false. [Failure builder](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/provider-core/src/server/failure.ts#L308-L342), [terminal error and retry item builders](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/provider-core/src/server/failure.ts#L344-L442).

Internal runs also carry `activeAttemptId`, `restartContinuationOfRunId`, `manualContinuationOfRunId`, and `usageLimitContinuationOfRunId`; attempts carry reason (`initial`, `steering_restart`, `retry`, or `provider_recovery`) and status. Public summaries omit all of them. Provider-level retry within a turn is not necessarily a new T3 run or a new run attempt. [Run schema](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/orchestrationV2.ts#L819-L844), [attempt schema](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/orchestrationV2.ts#L878-L905).

## Provider differences

- **Codex:** the adapter consumes native `error.willRetry`, preserving non-retrying error codes for terminal classification. The retry path emits a running error item; max attempts can be unknown and delay is not reported for native retry. HTTP 429 and usage/rate-limit codes map to usage limit, selected disconnected stream errors to transport, and other errors to a broad provider class. A model-capacity failure can also trigger T3's own delayed native turn restart within the same run. Terminal failure retains retry history and can use a previous notification to classify an ambiguous completion error. [Notification handling](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L5598-L5659), [classification](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L1364-L1401), [terminal failure](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L6810-L6893), [capacity retry](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L7650-L7714).
- **Claude:** SDK `api_retry` messages provide attempt count, limit, and delay. The terminal result treats 429 as usage limit, 529 as overload, and other errors generally as provider errors, with unknown retryability when not explicitly determined. Some gateway reset times are extracted from text. Both Claude and Codex have T3 retry time budgets; the shared constant is ten minutes, not a general API guarantee for every provider. [Claude error mapping](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts#L5143-L5243), [retry notification](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts#L11780-L11828), [shared retry budget](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/provider-core/src/server/failure.ts#L385-L390).
- **ACP-based providers:** the generic adapter can report retries when a flavor supplies notices, counting observations with unknown maximum and delay. A generic prompt error or unfinished stop falls back to provider error; flavor-specific classification may override it. This is not evidence that every ACP agent emits retry notices or equivalent semantics. [Retry path](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/provider-acp/src/server/adapter.ts#L3191-L3218), [generic failure mapping](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/provider-acp/src/server/adapter.ts#L5866-L5889).
- **Antigravity:** its ACP adapter interprets its own session's error steps because the harness can report a service error as a chat message followed by normal end-of-turn. Quota exhaustion is usage-limit; account verification is non-retryable permission error; 404 classification depends on whether the model was reached; invalid saved thinking signatures can require a fresh native session despite `retryable: true`. Missing evidence leaves generic failure or weaker typed-only detection. [Outcome mapping and evidence boundary](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/provider/acp/AntigravityTurnOutcome.ts#L203-L291).

These differences prevent a universal transient/permanent classifier based on public error text. Even exposing existing normalized fields would give incomplete classification where a provider has no structured evidence.

## Native continuation

### Usage limits

T3's native worker checks that the latest run failed, the last normalized class is usage limit, a valid reset exists after completion, the thread is not archived or explicitly settled, and no runtime request is pending. Settings can arm recovery and/or snooze. Persisted metadata identifies the original run, reset time, auto-resume flag, snooze flag, and optional request ID. Once due, auto-resume dispatches a server-created continuation using deterministic identity and `usageLimitContinuationOfRunId`. An overdue newly armed reset is bounded to 24 hours; this is not an arbitrary retry cadence. [Recovery metadata](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/orchestrationV2.ts#L450-L472), [worker](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/UsageLimitRecoveryWorker.ts#L15-L78).

The [user guide](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/docs/user/thread-sidebar.md#L285-L305) confirms manual resume, scheduled resume at reset, overdue recovery after restart, and independent snooze. Stop, send, archive, or settle can prevent a pending continuation. Without a reset time, automatic usage-limit continuation is not supported by that worker. A runner observing only public read cannot distinguish an armed but unsnoozed continuation from an ordinary failed run, nor reliably link its subsequent run to the original one. A restart can renew an unsent recovery's request ID ([runtime recovery](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts#L594-L609)).

### Server and provider-runtime restart

The server reconciles interrupted runtime state. An unaccepted user-authored prompt can remain in a held queue; qualifying unattended MCP/scheduled prompts may be resent on the same run when restart continuation is enabled, with bounded resends. Other cut runs can be marked `cancelled`, with a system notice explaining the restart; a visible notice is not emitted for every cut. [Reconciliation](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts#L379-L485), [cancellation](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts#L677-L701), [notice](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts#L792-L820).

Accepted work can instead continue in a new run, or a previously completed/waiting run can receive a wake for lost awaited background work. The server prepares a continuation effect, conditioned on per-project settings, strong native identity, session/turn liveness, human requests, stop intents, and other guards. It rechecks the source before dispatch and limits repeated crashes; its generated message is linked by `restartContinuationOfRunId`. Provider exit can also trigger the path. [Eligibility](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/RestartContinuation.ts#L45-L91), [source selection](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/RestartContinuation.ts#L169-L239), [outbox effect](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts#L990-L1032), [dispatch guards and lineage](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/RestartContinuation.ts#L241-L358).

Unlike read, **public wait is restart-aware**: it traverses the restart lineage, checks pending continuation effects for terminal runs, and reports unsettled until they resolve. A different returned `runId` is therefore possible even without delegated-work settlement. The wait does not expose the pending reason or follow the usage-limit field in its outcome function. [Lineage traversal](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/ThreadManagementService.ts#L602-L613), [wait outcome](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/ThreadManagementService.ts#L1119-L1153), [public mapping](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/OrchestratorMcpService.ts#L3803-L3861).

## Comparison with Codex enhancement

The existing Codex monitor retains native `willRetry` for the latest matching turn and clears it for new turns. Recovery considers a failed latest turn on an idle or system-error thread only when `willRetry !== true`. It excludes specified string-valued `codexErrorInfo` values (session budget, usage limit, unauthorized, model missing, context window, policy failures), waits with bounded retries and rechecks the turn, Assignment, expected file and pause before invoking Core. It is a negative exclusion policy, **not** positive proof that all other errors are transient. [Observation](https://github.com/BuddyLabsCo/issue-runner-agent-codex/blob/7bffcb348c1fd7b6c0f75505f72ac2cabbf1040d/src/monitor/state.ts#L277-L322), [error exclusions and eligibility](https://github.com/BuddyLabsCo/issue-runner-agent-codex/blob/7bffcb348c1fd7b6c0f75505f72ac2cabbf1040d/src/recovery/error.ts#L12-L115), [recheck](https://github.com/BuddyLabsCo/issue-runner-agent-codex/blob/7bffcb348c1fd7b6c0f75505f72ac2cabbf1040d/src/recovery/error.ts#L315-L363).

A faithful comparison requires distinguishing run outcome, retryability, native recovery in progress/pending, and run identity. T3 public run status covers the first; activity items and restart-aware wait give partial information about the third. It lacks typed evidence equivalent to the Codex exclusion field, and T3 itself may continue work after a failed or cancelled run.

## Public API gaps and remaining validation

The smallest upstream interface changes that would close the evidence gaps are:

- Return structured, sanitized, run-associated terminal failure metadata (`class`, `code`, nullable `retryable`, reset time), and structured retry progress/state on error items, distinguishing active retry from history. Keep unknown distinct from false. Do not expose raw provider payloads or credential-bearing details.
- Expose native pending recovery state associated with a run and its kind (provider retry, usage-limit continuation, restart continuation/resend), including reset/deadline where known. Include durable continuation lineage in run summaries or a public run-detail operation. An atomically current ability to observe pending/claimed recovery would resolve ambiguities not addressed by a delay alone; a read followed by a send is still a race.
- Document which normalized fields and lifecycle guarantees providers actually support and when data is absent; expand classification coverage if parity needs distinctions hidden behind generic provider/unknown failures. Existing internal WebSocket projections or database tables are not a documented external monitoring contract.

Verify on representative providers with controlled acceptance cases for transient stream/overload, authentication/permission/context and other non-retryable failures, quota with and without reset, retry success and exhaustion, server restart before/after prompt acceptance, native continuation cancellation and reconnect. Include exact run linkage, background work, queue and human request state; verify whether public wait returns the continued run in the actual interface. No cases were executed for this report. The evidence gaps and proposed interface additions do not select Runner's recovery policy or prescribe a retry budget.
