# T3 Assignment completion and human-action signals

Research for [#53](https://github.com/BuddyLabsCo/issue-runner-t3/issues/53), against T3 Code [v0.1.12](https://github.com/pingdotgg/t3code/tree/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd) (November 25, 2026) and the existing [Codex enhancement](https://github.com/BuddyLabsCo/issue-runner-agent-codex/tree/7bffcb348c1fd7b6c0f75505f72ac2cabbf1040d). The findings come from pinned source, public contracts, documentation, and existing upstream tests. No live agent runs or failure injection were performed.

Public MCP can establish observed thread quiescence and retrieve complete text for a known timeline item. It cannot independently prove that the thread's latest result belongs to a particular Assignment, that an assistant message is a final answer, or that every future native wake or human request has been accounted for. These are distinct evidence gaps, not recovery-policy decisions.

## Thread quiescence

| Public signal | What it establishes and what it does not |
| --- | --- |
| `t3_thread_read`: `thread.status`, `activeRunId`, `latestRunId`, `recentRuns` | Active statuses are `preparing`, `starting`, `running`, `waiting`. Terminal run statuses are `completed`, `failed`, `cancelled`, `interrupted`, `rolled_back`. `queued` is separate from active. The thread projection prefers the active run to the latest run by ordinal; a later cancelled run can coexist with an earlier active one. A failed latest run also takes precedence over awaiting background work. [Implementation](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/OrchestratorMcpService.ts#L995-L1112), [run predicates](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/ThreadManagementService.ts#L573-L621). |
| `t3_queue`, `action: list` | Lists queued runs in delivery order, including held work, independent of active-run detection. Inspect `items` and `nextCursor`; an empty first page with no cursor is the ordinary empty queue response. The handler reads run/message records separately and skips an entry if its message is missing. Default page size 20, maximum 100; list text is capped at 1,000 Unicode code points. [Contract and handler](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/toolkits/thread/handlers.ts#L312-L345), [entry projection](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/toolkits/thread/handlers.ts#L30-L43). |
| `blockedOnThreadWait`, `pendingBackgroundTasks` | The former detects a running turn whose executing tool work consists of thread waits or blocking delegation. The latter lists known subagents, commands, monitors and other background tasks, including child thread IDs when available. Subagents and `background_task` hold completion; commands and monitors hold it only when `awaited: true`. A released dev server or passive PR watch can remain in the list. The roster may be empty while an active run is executing. Older linked peers may omit both fields. [Public contract](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/orchestratorMcp.ts#L387-L429), [derivation and completion predicate](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/shared/src/orchestrationV2PendingBackgroundWork.ts#L57-L121), [roster computation](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/shared/src/orchestrationV2PendingBackgroundWork.ts#L261-L355). |
| `t3_thread_wait` with `runId`, `untilDelegatedWorkSettled: true` | Waits first for the selected run, following native restart continuations, then for thread-wide work and result delivery. A completed original run can still time out. `resultRun` identifies the result of the thread-wide wait, not necessarily the original run's descendant. [Contract](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/orchestratorMcp.ts#L585-L616), [implementation](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/ThreadManagementService.ts#L1105-L1245). |
| `settled` / `settledAt` | Thread organization state, separate from active work or an Assignment result. [Projection](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/OrchestratorMcpService.ts#L920-L928). |

The delegated wait checks active children, their pending or claimed completion deliveries, and provider-reported background tasks that hold completion. Its result calculation excludes rolled-back runs, monitor-update-only runs and some held queue entries; notably, held agent/system wakes do not necessarily block this wait. The server also checks in-flight delegated-result delivery. A queued run can therefore still exist after a successful delegated wait, and an unawaited monitor can keep running. [Delegated progress calculation](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/provider-core/src/server/subagentProjection.ts#L382-L443). Upstream tests explicitly cover active-versus-latest runs and an unawaited dev server ([MCP read tests](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/OrchestratorMcpService.activity.test.ts#L246-L297)), and a delegated wake whose response belongs to a different run ([wait test](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/ThreadManagementService.test.ts#L389-L473)).

The wait's default deadline is 30s, clamped to 1–45,000 ms. `timedOut: true` means the requested condition has not been established, not failure. The thread read itself fetches [shell and run/request records](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/OrchestratorMcpService.ts#L1585-L1635) and timeline separately, and a queue read is another call. There is no public transaction or observation version spanning those calls. The existing adapter already reads thread, then queue, then thread again for resume and archive ([terminal adapter](https://github.com/BuddyLabsCo/issue-runner-t3/blob/539038cf4ea8ea23609554e98bcc32ebea625553/src/terminal.ts#L105-L161)). Repetition can expose races but is not an atomic guarantee.

## Attribute a result to an Assignment, not merely to a thread

The `t3_thread_send` receipt contains `threadId`, `messageId`, `runId`, native status and delivery (`started`, `queued`, `steered`, `restarted`). It is the direct attribution evidence for a submitted prompt. The current adapter supplies a random `clientRequestId` for each logical send and checks these IDs, but discards the receipt ([adapter](https://github.com/BuddyLabsCo/issue-runner-t3/blob/539038cf4ea8ea23609554e98bcc32ebea625553/src/terminal.ts#L271-L295), [send contract](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/orchestratorMcp.ts#L553-L583)). Steering can share a run with other prompts; a native restart can change the run ID returned by wait. Neither the run's ordinal nor its timestamp proves Assignment identity.

T3's own CLI illustrates the limit. Its `waitForRun` first waits for the exact submitted run, then follows delegated work only for a completed run and a send preceded by an idle check. Unlike the adapter, the CLI [explicitly uses queue delivery](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/cli/thread.ts#L1023-L1037). Before using `resultRun`, it checks later runs for a `user_message` in the messages view. Notifications that trigger background wakes are not ordinary user messages. If another prompt appeared or the original run is no longer in the recent 50, it retains the original run's result rather than borrowing the newest one. If work outlived that run, the CLI also polls every 500 ms for up to 10s to bridge the gap between provider work ending and its wake-run record appearing. These are upstream heuristics, not proof that a notification belongs to one Assignment or that no future wake can occur. [CLI implementation](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/cli/thread.ts#L580-L718), [test cases](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/cli/thread.test.ts#L330-L450).

Public `recentRuns` lacks the internal run's restart-continuation relationship, delegated-task relationship and triggering message ID. Timeline rows expose `runId`, `messageId`, `sourceThreadId`, `visibility`, `senderThreadId` and message provenance, so an exact receipted prompt can be verified and a foreign prompt detected. The public projection does not expose structured parent-run attribution for automatic wakes. [Run and timeline schemas](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/orchestratorMcp.ts#L508-L551).

## Identify complete reply text

`t3_thread_read` supports `messages` and `activity`. The former includes user/assistant messages and proposed plans; the latter includes tool and request items. Read the newest page by default; `beforePosition` retrieves older entries and `afterPosition` retrieves newer ones (start at `-1`). Positions refer to the full visible timeline, so a filtered page can contain gaps. The server returns `earlierPosition`, `nextPosition` and `hasMore`; latest-page `hasMore: false` does not establish that there are no earlier entries. Defaults are 10 timeline items, 10 recent runs, 500 characters per item; maxima are 100, 50 and 20,000. `recentRuns` is always the latest run window, not paged by item positions. The public read has no `runId` selector for historical run details, although wait accepts an exact run ID. [Read schema](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/orchestratorMcp.ts#L446-L459), [server paging](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/OrchestratorMcpService.ts#L3624-L3746), [visible positions](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/ProjectionStore.ts#L8053-L8123).

The server targets a 30,000-byte response budget and can shorten a page or truncate text further. For a selected item, page text via `itemId` and `textOffset: nextTextOffset` until `textTruncated` is false. Offsets use JavaScript string units and avoid splitting surrogate pairs. `textOffset` applies only with `itemId`. Matching source thread, run, item and update timestamp across chunks distinguishes a stable result from an item changed during reading. An incremental position cursor cannot reveal a text or status update at a previously read position. [Text projection and response budget](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/OrchestratorMcpService.ts#L1235-L1357), [default limits](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/OrchestratorMcpService.ts#L146-L167), [CLI full-text retrieval](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/cli/thread.ts#L515-L557).

The Codex enhancement checks the last `agentMessage` whose phase is absent or `final_answer`, tied to its Assignment, before interpreting a leading `[action required]` marker. It deduplicates by turn/item. [Codex source](https://github.com/BuddyLabsCo/issue-runner-agent-codex/blob/7bffcb348c1fd7b6c0f75505f72ac2cabbf1040d/src/recovery/error.ts#L124-L149). T3's internal assistant items have `phase`, `delivery` and `streaming`, but the external MCP timeline has none. It has `status`, so a completed local `assistant_message` from the attributed run can be read in full. The CLI finds the last assistant message with that run ID (and prints it only on completion); this is an approximation, not equivalent to identifying a distinct final answer. The public API cannot reliably distinguish a completed commentary item, a partial answer or async delivery from the final response. A completed run may also contain no reply. [Internal item schema](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/orchestrationV2.ts#L1932-L1943), [public projection](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/OrchestratorMcpService.ts#L1265-L1284), [CLI result](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/cli/thread.ts#L733-L766).

## Native human requests and events

`pendingRequestCount` counts all pending runtime requests on the thread, not only human questions or approvals. The runtime schema includes `dynamic_tool_call`, `auth_refresh`, `user_input` and provider request kinds. `t3_pending_request(list)` returns IDs for pending `user_input` only; `read` returns that request's questions and rejects resolved/expired/cancelled requests. It does not list approval or MCP elicitation requests. The tool's response operation is not an approval interface. A nonzero count signals outstanding runtime requests, while a zero question list is not evidence that approval is unnecessary. The CLI rechecks its exact run after seeing a nonzero count, because a pending request may belong to a later run or an earlier run blocking the queue ([CLI logic](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/cli/thread.ts#L652-L669)). The activity timeline can identify `approval_request` and `user_input_request` items by type/run/status and read text, but does not expose their structured request ID or response capability. [Runtime schema](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/orchestrationV2.ts#L1415-L1440), [pending question handler](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/toolkits/thread/handlers.ts#L248-L284), [question read checks](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/toolkits/thread/handlers.ts#L70-L95).

T3 also records waiting `secret_request`, `feedback_request` and `link_request` cards as turn-item updates, independently of runtime request count. Activity reads expose their type, status and redacted descriptive text. Native requests from a child thread may require a child-specific read; the parent's count does not aggregate its descendants. The card records and the absence of an all-descendant request index limit completeness of a parent-only observation. [Card projections](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/Orchestrator.ts#L11183-L11242), [feedback](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/Orchestrator.ts#L11299-L11341), [link](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/Orchestrator.ts#L11420-L11476), [MCP text mapping](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/mcp/OrchestratorMcpService.ts#L1162-L1232).

The external MCP Events extension (`io.modelcontextprotocol/events`) exposes milestones, not the complete orchestration event stream. `thread.run_settled` identifies a run and outcome, but excludes rollback and runs without start/completion timestamps. `thread.needs_input` and `thread.input_resolved` identify the thread and request, not a run ID. They map command/file/permission prompts to approval and user input/MCP elicitation to questions; other runtime kinds and separate request cards do not emit these milestones. Resolution can mean resolved, expired or cancelled, not necessarily human approval. The public event extension does not cover each run start, queue change, message update, or task-delivery transition. Child events are muted unless requested; the buffer retains 1,000 milestones in memory and subscriptions last at most an hour. A gap or service restart requires rereading observed state. [Event schema](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/packages/contracts/src/milestones.ts#L32-L78), [emitter](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/milestones/OrchestrationMilestones.ts#L25-L38), [transition coverage](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/milestones/OrchestrationMilestones.ts#L130-L219), [external documentation](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/docs/user/outside-agents.md#L119-L139).

## Remaining uncertainties

- Provider-specific task reporting differs. In particular, Claude's `ScheduleWakeup` does not enter its background roster, and an ordinary monitor wake has no task notification frame. A public snapshot cannot guarantee that the provider will not wake again. [Claude adapter](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts#L6512-L6524).
- Internally Codex retains native phase, and Claude marks known final answers; external readers cannot access that phase through the timeline. Whether each supported provider reliably represents its full final reply, native children, approvals and background activity requires provider-specific acceptance evidence. [Codex adapter phase handling](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L6247-L6255), [Claude assistant item](https://github.com/pingdotgg/t3code/blob/ca81b7b97a1c4b91e5ac25768d0f6629f37732fd/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts#L5325-L5337).
- The public interface lacks an atomic Assignment attribution, complete reply-phase distinction, and complete request/wake roster. Native thread/queue/delegated-wait/timeline evidence can be combined, but a mismatch, missing page, concurrent prompt, disconnected observer or unknown provider capability remains uncertainty. Neither a milestone nor a terminal run alone establishes readiness for a recovery decision. This report leaves classification, delay, pause/resume behavior and policy to later design work.
